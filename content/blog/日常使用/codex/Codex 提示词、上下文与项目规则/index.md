## 一、为什么提示词决定了 Codex 的上限

同一个 Codex，同一个仓库，换一种说法，结果可能完全不同。原因很简单：**Codex 的产出质量，约等于你提供的任务信息质量**。

一段含糊的提示词：

```text
帮我优化一下订单模块
```

它至少缺了四样东西：

- **目标**：优化什么？性能、可读性，还是减少重复代码？
- **范围**：只动订单模块，还是允许改公共类？
- **约束**：能不能改接口签名？能不能加依赖？
- **验收**：怎么算做完？测试通过，还是压测 QPS 达标？

所以提示词的核心不是"写得长"，而是**把隐含信息显式化**。

## 二、如何描述开发任务与验收标准

### 2.1 一个够用的任务模板

```text
【目标】一句话说明要达成什么。
【背景】相关业务逻辑、历史原因、上下游影响。
【范围】允许改哪些文件 / 模块；哪些绝对不能碰。
【约束】接口签名、依赖、兼容性、性能要求。
【验收】怎么验证：跑什么命令、期望什么结果。
【输出】要代码还是要方案；要不要先给计划。
```

### 2.2 把验收标准写具体

模糊：

```text
把这个接口改快一点
```

具体：

```text
把 GET /orders/{id} 的 P99 从 800ms 降到 200ms 以内。
不允许改接口返回结构；不允许加新的外部依赖。
验收方式：本地跑 JMeter 脚本 load-test/order.jmx，报告 P99 < 200ms。
```

### 2.3 用"完成后请给出证据"收口

```text
完成后请贴出：1) git diff --stat；2) 运行测试的命令与结果；3) 你验证过的边界情况。
```

要求证据，能显著减少"看起来改了其实没验证"的情况。

## 三、任务背景、约束条件与输出格式

### 3.1 背景怎么写

背景不是写日记，只写**会影响决策**的信息：

```text
背景：
- 这个服务下个月要拆成两个微服务，所以不要把新逻辑耦合进单体模块。
- 上游还在用旧版本的 SDK，暂时不能升级大版本。
- 线上是 Java 17，本地开发可能装了 21，注意不要用 21 的语法。
```

### 3.2 约束怎么写

约束要写成**可判定的规则**，而不是感觉：

| 弱约束 | 强约束 |
| --- | --- |
| 尽量别改太多 | 最多修改 3 个文件，不允许改 `pom.xml` |
| 注意性能 | 循环里禁止数据库查询，禁止 N+1 |
| 保持风格 | 参照 `UserService` 的写法，使用构造器注入 |

### 3.3 输出格式怎么写

```text
输出要求：
1. 先给 5 行以内的结论；
2. 再给改动方案（文件级）；
3. 最后给风险点；
4. 不要输出完整代码，除非我要求。
```

对结构化场景，可以让 `codex exec` 直接输出 JSON（第四篇会讲 `--output-schema`）。

## 四、大型项目的上下文组织

### 4.1 不要一次性把整个项目塞进去

大仓库里，正确的做法是**分层提供上下文**：

1. **仓库级**：`AGENTS.md` 说明技术栈、构建命令、约定。
2. **模块级**：进入具体模块目录再开任务，或显式点名模块。
3. **文件级**：用 `@` 把关键文件插进提示词。
4. **片段级**：只贴真正相关的方法或报错。

### 4.2 用 `@` 精确投喂

在输入框输入 `@`，搜索并插入文件路径：

```text
参照 @src/main/java/com/example/order/OrderService.java 的风格，
在 @src/main/java/com/example/refund/ 下实现 RefundService。
```

### 4.3 让 Codex 自己建立"地图"

任务开始前先要一份地图，后续所有对话都建立在这份地图上：

```text
只读分析，输出：
1. 模块清单与职责；
2. 关键类的调用关系（用文字箭头表示）；
3. 数据流向：从 HTTP 入口到数据库；
4. 这份地图存到 docs/codex-map.md。
```

把结论落成文件后，后续会话可以直接 `@docs/codex-map.md`，不必每次重新分析。

## 五、分析、计划、实现、验证的分阶段工作流

一个可靠的四阶段流程：

```text
阶段一（分析）：只读。找出相关代码、调用链、风险点。不要改任何文件。
阶段二（计划）：给出文件级改动方案和验收方式。等我确认。
阶段三（实现）：按计划改代码，只改计划内的文件。
阶段四（验证）：运行测试/构建，贴出命令与结果；说明未覆盖的部分。
```

### 5.1 用 `/plan` 强制先规划

```text
/plan 把订单创建的同步扣库存改成异步消息，给出迁移计划
```

计划模式下 Codex 只出方案、不动手，非常适合改动较大的任务。

### 5.2 分阶段推进的实际节奏

```text
第一轮：codex "只读分析，列出与登录相关的类和它们的职责"
第二轮：codex "基于上面的分析，给出把 JWT 换成 Sa-Token 的改动计划，不要改代码"
第三轮：codex "按计划实现第一步：替换依赖并调整配置"
第四轮：codex "跑 mvn test，修复失败用例，贴出结果"
```

每一轮都基于上一轮的产物，比一次性丢一个大需求稳得多。

## 六、如何指定文件与代码范围

### 6.1 三种指定方式

```text
# 方式一：显式路径
只修改 src/main/java/com/example/user/UserService.java。

# 方式二：目录范围
只允许修改 user 包下的文件，不要动 common 包。

# 方式三：排除法
可以改 service 和 mapper，禁止改 controller、实体类和 pom.xml。
```

### 6.2 让范围可校验

```text
完成后运行 `git diff --name-only`，
如果出现范围外的文件，请回滚这些改动并说明原因。
```

### 6.3 处理"必须改到范围外"的情况

```text
如果你认为必须修改范围外的文件，先停下来告诉我：
要改哪个文件、为什么必须改、有什么替代方案。得到确认后再动手。
```

这条规则能有效防止"顺手重构"。

## 七、如何要求 AI 先分析再修改

### 7.1 标准话术

```text
先不要改代码。请先：
1. 复述你对任务的理解；
2. 列出你会修改的文件；
3. 指出你不确定的地方。
等我确认后再实现。
```

### 7.2 用"复述"检验理解

让 Codex 复述任务，是成本最低的纠偏手段。如果它的复述就跑偏了，说明提示词有问题，这时改提示词比让它改代码划算得多。

### 7.3 只读模式兜底

```bash
codex --sandbox read-only --ask-for-approval on-request "分析这个 Bug 的可能原因"
```

在只读沙箱里，它物理上就改不了文件，可以放心让它自由探索。

## 八、如何控制改动范围，避免过度重构

### 8.1 明确写进约束

```text
约束：
- 只做需求要求的最小改动；
- 不要顺手重构、不要重命名、不要调整格式；
- 不要升级依赖版本；
- 不要新增抽象层（接口/工厂/策略）除非我明确要求。
```

### 8.2 用 diff 审查改动

```bash
git diff --stat
git diff
```

发现超范围改动时：

```text
你在 UserService 之外还改了 5 个文件，其中 3 个与本次需求无关。
请回滚无关改动，只保留必要的最小集合。
```

### 8.3 常见"过度发挥"及对策

| 表现 | 对策 |
| --- | --- |
| 顺手格式化了整个文件 | 约束里写"不要调整格式"，审查时用 `git diff -w` 排除空白差异 |
| 新增了不必要的接口 / 抽象 | 明确"不要新增抽象层" |
| 升级了依赖版本 | 明确"不要改 `pom.xml` / `package.json`" |
| 改了公共类签名 | 明确"公共 API 签名不可变" |
| 加了未要求的日志 / 注释 | 要求"不加非必要注释" |

## 九、长会话中的上下文管理

### 9.1 上下文会衰减

会话越长，早期信息越容易被稀释或截断。表现为：Codex 开始忘记你最早定的约束。

### 9.2 四个应对手段

1. **把约定落成文件**：写进 `AGENTS.md`，而不是只在对话里说过。
2. **把中间结论落盘**：分析结果写进 `docs/`，需要时 `@` 回来。
3. **阶段结束就 `/clear`**：一个阶段一个新会话，避免历史包袱。
4. **定期复述约束**：长任务里隔几轮重申一次关键约束。

```text
提醒一下本次任务的硬约束：不改接口签名、不加依赖、只改 service 包。
```

### 9.3 什么时候该开新会话

- 话题从"分析"切到"实现"，且分析结论已落盘。
- 连续两三轮都在纠正同一个误解。
- 你发现它在引用过时的信息。

## 十、错误示例与提示词迭代方法

### 10.1 三个典型错误

```text
❌ 帮我把这个项目优化一下
❌ 有个 Bug，你看看
❌ 照着这个需求做完
```

分别缺的是：目标与验收、现象与复现、需求细节与边界。

### 10.2 迭代方法：一次只改一个变量

```text
第 1 版：把用户查询接口改快一点
→ 结果：它优化了 SQL，但没给证据

第 2 版：把用户查询接口改快一点，完成后贴出执行计划 EXPLAIN
→ 结果：给了执行计划，但改了接口返回结构

第 3 版：把用户查询接口改快一点，完成后贴出 EXPLAIN；
        不允许改接口返回结构；不允许加新依赖
→ 结果：符合要求
```

每次只补一个缺失的信息，就能定位到底是哪一条约束在起作用。

### 10.3 把好提示词存下来

把反复用到的提示词整理成模板，放在仓库里：

```text
docs/prompts/
├── analyze-module.md
├── implement-feature.md
└── fix-bug.md
```

需要时 `@docs/prompts/fix-bug.md` 加一句话即可。

## 十一、AGENTS.md 的作用与使用方式

前面讲的所有"约束"，如果只写在对话里，开一个新会话就没了。`AGENTS.md` 就是把这些约定**固化到文件里**，让 Codex 每次启动都自动加载。

Codex 在动手之前会先读 `AGENTS.md`。它按下面的顺序构建指令链（每次运行构建一次，TUI 里通常是每次启动会话构建一次）：

1. **全局**：`$CODEX_HOME`（默认 `~/.codex`）下的 `AGENTS.override.md`，没有才读 `AGENTS.md`，这一层只取第一个非空文件。
2. **项目**：从项目根（一般是 Git 根）一路向下走到当前工作目录，每个目录依次找 `AGENTS.override.md` → `AGENTS.md` → `project_doc_fallback_filenames` 里配置的备用文件名，**每个目录最多取一个文件**。
3. **合并**：从根往下拼接，越靠近当前目录的规则越靠后，优先级越高。

Codex 会跳过空文件；合并后总大小超过 `project_doc_max_bytes`（默认 32 KiB）就不再往下加。

### 11.1 最小的项目级 AGENTS.md

```md
# AGENTS.md

## 项目说明
- 这是一个 Spring Boot 3 + Java 17 的单体应用，构建工具是 Maven。

## 常用命令
- 构建：`./mvnw -q -DskipTests package`
- 单测：`./mvnw test`
- 只跑某个类：`./mvnw test -Dtest=OrderServiceTest`

## 编码约定
- 使用构造器注入，不用 `@Autowired` 字段注入。
- 公共方法必须有 Javadoc；不要给私有方法加无意义注释。
- 新增依赖前必须先问我。
```

### 11.2 全局 AGENTS.md

```bash
mkdir -p ~/.codex
${EDITOR:-vim} ~/.codex/AGENTS.md
```

```md
# ~/.codex/AGENTS.md

## 通用约定
- 回答用中文，结论放最前面。
- 修改代码后主动运行相关测试。
- 不确定时先问，不要猜。
```

### 11.3 验证规则是否被加载

```bash
codex --ask-for-approval never "Summarize the current instructions."
codex -C services/payments --ask-for-approval never "列出你加载了哪些指令文件"
```

预期输出会按"全局 → 仓库根 → 子目录覆盖"的顺序列出。

## 十二、全局规则与项目规则的组织

### 12.1 分工原则

| 层级 | 放什么 | 例子 |
| --- | --- | --- |
| 全局 `~/.codex/AGENTS.md` | 个人偏好，跨仓库通用 | 回答语言、测试习惯、提问风格 |
| 仓库根 `AGENTS.md` | 团队共享约定 | 技术栈、构建命令、编码规范 |
| 子目录 `AGENTS.md` | 局部特殊规则 | 某个服务的测试命令、特殊禁令 |

判断标准很简单：**这条规则换个仓库还成立吗？** 成立就放全局，不成立就放项目。

### 12.2 临时覆盖

需要在全局临时加一条规则、又不想动原文件时，用 `~/.codex/AGENTS.override.md`，用完删掉即可恢复。

### 12.3 用备用文件名兼容既有仓库

团队已经在用 `TEAM_GUIDE.md` 之类的文件名，可以在配置里登记：

```toml
project_doc_fallback_filenames = ["TEAM_GUIDE.md", ".agents.md"]
project_doc_max_bytes = 65536
```

这样 Codex 会按 `AGENTS.override.md` → `AGENTS.md` → `TEAM_GUIDE.md` → `.agents.md` 的顺序查找。

## 十三、多模块项目中的规则继承

多模块仓库最典型的用法是"根规则 + 模块覆盖"。

```text
my-platform/
├── AGENTS.md                     # 全仓：技术栈、通用命令、编码规范
├── services/
│   ├── order/
│   │   ├── AGENTS.md             # 订单服务：专用测试命令
│   │   └── src/...
│   └── payments/
│       ├── AGENTS.override.md    # 支付服务：覆盖通用规则
│       └── src/...
```

根 `AGENTS.md`：

```md
## 全仓约定
- 所有模块统一用 `./mvnw`。
- 提交前必须通过 `./mvnw -q verify`。
```

`services/order/AGENTS.md`：

```md
## 订单服务
- 单测命令是 `./mvnw -pl services/order test`。
- 订单状态机相关改动必须同步更新 `docs/order-state.md`。
```

从 `services/payments` 目录启动时，Codex 会把全局、根、支付三层规则按顺序拼起来。

> 关键点：Codex **只走到当前目录为止**。所以规则要尽量放在离实际工作最近的地方。

## 十四、技术栈、编码规范与兼容性要求

### 14.1 技术栈写清楚

```md
## 技术栈
- Java 17，Spring Boot 3.2，Maven 3.9。
- 数据库 PostgreSQL 15，ORM 用 MyBatis-Plus。
- 前端 Vue 3 + Vite，包管理器 pnpm。
```

不写技术栈，Codex 可能用 Java 21 的语法、或者用 Gradle 命令，白折腾一轮。

### 14.2 编码规范写成可执行规则

```md
## 编码规范
- 使用构造器注入；禁止 `@Autowired` 字段注入。
- DTO 与实体分离，Controller 层不直接返回实体。
- 统一用 `Result<T>` 包装返回值。
- 异常统一抛 `BizException`，不要抛裸 `RuntimeException`。
- 禁止在循环里做数据库查询。
```

### 14.3 兼容性要求

```md
## 兼容性
- 线上是 Java 17，不要使用 Java 21 及以上语法。
- 公共 API 的入参和返回值签名不可变。
- 不要升级任何依赖的主版本号。
- 需要兼容 MySQL 5.7 与 PostgreSQL 15 两种部署。
```

## 十五、测试命令、构建命令与验收标准

把命令写进 `AGENTS.md`，能省掉每次解释，也让验收可复现。

```md
## 常用命令
| 目的 | 命令 |
| --- | --- |
| 编译 | `./mvnw -q -DskipTests compile` |
| 全量测试 | `./mvnw -q test` |
| 单类测试 | `./mvnw -q test -Dtest=OrderServiceTest` |
| 静态检查 | `./mvnw -q spotbugs:check` |
| 打包 | `./mvnw -q -DskipTests package` |

## 验收标准
- 改动完成后必须运行全量测试，并贴出命令与结果。
- 不允许用 `-DskipTests` 绕过测试。
- 不允许修改测试断言来"让测试通过"；测试确实写错时先说明。
```

前端项目同理：

```md
## 常用命令
- 安装依赖：`pnpm install`
- 类型检查：`pnpm typecheck`
- 单测：`pnpm test --run`
- 构建：`pnpm build`
```

## 十六、约束 AI 只修改必要文件

### 16.1 直接在规则里写死

```md
## 改动范围
- 只修改与当前任务直接相关的文件。
- 禁止格式化无关文件、禁止批量重命名、禁止调整 import 顺序。
- 需要修改以下文件时必须先征求同意：`pom.xml`、`package.json`、
  `src/main/resources/application.yml`、任何 `*.sql`。
```

### 16.2 让 Codex 自己报告越界

```md
## 交付要求
- 完成后运行 `git diff --name-only`。
- 如果出现了预期之外的文件，主动回滚并说明原因。
```

### 16.3 配合审查命令

```bash
git diff --stat
git diff -w          # 忽略空白差异，专门看逻辑改动
git diff --name-only
```

## 十七、规则文件的维护与精简

规则不是越多越好。太长会挤占上下文，还可能自相矛盾。

### 17.1 精简四条原则

1. **一条规则只写一件事**，能判定对错。
2. **删掉 Codex 默认就会做对的**（例如"写清晰的代码"）。
3. **能进 CI 的交给 CI**：格式、lint 这类机械检查不必写进 `AGENTS.md`。
4. **过期就删**：技术栈升级后及时更新，避免误导。

### 17.2 控制体积

```toml
project_doc_max_bytes = 65536
```

如果规则确实很多，**拆到嵌套目录**比堆在一个大文件里更好——既避开体积上限，也让规则更精准。

### 17.3 定期体检

```bash
codex --ask-for-approval never "列出你加载的所有指令文件，并指出其中互相矛盾或过时的条目"
```

## 十八、通过真实任务验证规则是否有效

规则写完不等于生效。用真实任务做一次"验收"：

### 18.1 三个验证任务

```text
# 验证一：构建命令是否正确
codex --ask-for-approval never "不要改代码，告诉我这个项目怎么跑测试，然后实际跑一次最小测试。"

# 验证二：编码规范是否被遵守
codex "在 user 包下新增一个 UserQueryService，遵循项目约定。"
# 检查：是否用了构造器注入？是否加了多余注释？

# 验证三：改动范围是否被约束
codex "修复 UserService 里的空指针问题。"
# 检查：git diff --name-only，是否只动了预期文件？
```

### 18.2 没生效怎么办

| 现象 | 排查 |
| --- | --- |
| 规则完全没加载 | 确认目录正确、文件非空；`echo $CODEX_HOME` 看是否指到了别的 home |
| 加载了旧的规则 | 找找上层是否有 `AGENTS.override.md` 覆盖了它 |
| 规则被截断 | 提高 `project_doc_max_bytes`，或拆分到嵌套目录 |
| 备用文件名不生效 | 检查 `project_doc_fallback_filenames` 拼写，重启会话 |

> 规则文件没有缓存，每次运行都会重建指令链。改完重开会话即可，不需要"清缓存"。
